# AXS15231B (QSPI panel with its own touch)

320x480 QSPI display controller with an integrated touch controller, on the Guition JC3248W535 (3.5", ESP32-S3,
16 MB flash, 8 MB octal PSRAM). Not in OWLOS Flight Radar. Everything here is [docs]: read from FusionEdge's
tested driver (`src/displays/lgfx/panel_axs15231b.h`, `touch_axs15231b.h`, `lgfx_base.h`,
`AXS15231B_options/`), whose final stabilisation and overnight tests were done by a FusionEdge contributor on a
real board. Not run here. Board file: [jc3248w535](../../../esp32-boards/references/boards/jc3248w535.md).

Sureness words as in [SKILL.md](../../SKILL.md). The touch half: [touch/axs15231b](../touch/axs15231b.md).

## The bus

- Quad SPI: clock, CS and four data lines, no DC line (`pin_dc = -1`); `LGFX_USE_QSPI`. 40 MHz write, 16 MHz
  read (FusionEdge's other SPI panels: 27 and 12).
- A command goes out as `0x02`, then the command byte as a 24-bit address (`0x00, cmd, 0x00`), then its data.
- Pixels go out as `0x32`, then `0x00, 0x2C, 0x00` (RAMWR as the address), then the pixel stream on four lines.
- The vendor's driver re-sends CASET (0x2A) before every bitmap transfer and deliberately omits RASET in QSPI
  mode. FusionEdge sends the full 320-pixel CASET window before every frame; it also resets a controller write
  pointer that may have slipped by a pixel during the frame before.
- Some batches ignore the window commands altogether (BOARDS-WANTED.md): send whole frames from PSRAM.

## How FusionEdge keeps it stable

- A whole 320x480 frame in PSRAM, landscape in memory; the panel stands, so the frame is sent column by
  column from the right (the panel's rows).
- A background flush task that coalesces: drawing marks the frame dirty, the task waits one tick so several
  pushes from one UI pass become one physical frame. A fixed 60 Hz pacing made scrolling visibly slow.
- At most one physical full frame every 50 ms (`AXS_MIN_FRAME_INTERVAL_MS`). Drawing itself is not limited.
- No DMA for the frame transfer (`AXS_FLUSH_USE_DMA 0`): the S3's DMA path can very rarely lose or duplicate
  part of a long QSPI transfer without reporting an error.
- Staging blocks of 12,800 pixels (40 of the panel's 320-pixel rows), and each block is waited for before its
  buffer is reused.
- LovyanGFX's own automatic framebuffer display path is off: on the S3 it calls `display()` at the end of every
  primitive, which beside the flush task made a flush storm under spectrum updates, starved IDLE0 and let the
  task watchdog reset the board.
- After boot, a wake or an inversion change, the next 80 flushes send whole frames.
- Inversion in software: INVOFF is sent and every pixel is XORed with 0xFFFF on the way out. The panel's
  `invert` setting is forced off.
- `USE_BUILTIN_LED` must stay off on this module (FusionEdge's options say so).

## The settings that ran there

- ESP32-S3 with 16 MB flash and 8 MB OPI PSRAM, pioarduino platform-espressif32 55.03.37, Arduino ESP32 3.3.7,
  LovyanGFX 1.2.25, an overnight test with the spectrum on.
- Pins and the rest of the board: the board file above.
